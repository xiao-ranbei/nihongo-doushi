## 1. 工作流概述

两次追加功能都是「**先定口径、再落规格、后写代码**」的同一套流程，区别在于**改动对象**与**数据层是否扩展**。

| | 第一次追加 | 第二次追加 |
|---|---|---|
| 一句话目标 | 答题从「输入式」改为「选择题」，并接入应用图标 | 底栏收敛为「主页 / 我的」两标签，并补齐学习数据采集 |
| 性质 | **新建模块 + 重构单个界面** | **重构信息架构 + 扩展数据模型** |
| 起点 | 关子的四点重设计反馈 → 三版原型 → 选定 A + 抽屉 + 图标方向 1 | 关子定向「主页 V3 周历条 + V1 大卡、我的 V3、扩采集、清零迁移」 |
| 落地提交 | `82af946`（+ `13862d6` `c5ed026` `0a894f0` 三次口径对齐） | `7c4acb7` |
| 测试基线 | 22 → 29 → 31 | 31 → **36** |
| 存储层 | **无新增**（沿用既有四个键） | **新增两个键**（`history-v1`、`progress-v1`）+ 启动回填 |

共同骨架（两次完全一致，可作为后续追加功能的流程模板）：

```
① 需求定调  → ② 口径/规格固化 → ③ 分层实现（引擎 → 状态 → UI）
→ ④ 穷举单测 → ⑤ 模拟器实测（含读设备存储核对）→ ⑥ 提交推送
```

## 3. 第二次追加：两标签重设计 + 三项采集

### 3.1 目标

1. 底栏仅保留「主页 / 我的」两个标签，切换清晰、选中态明显
2. 主页作各功能模块的统一入口
3. 我的页展示今日学习统计（时长、完成任务数、学习进度）
4. 扩采集相关功能

| 3 | 关子选定：主页 = V3 周历条 + V1 大卡；我的 = V3；扩采集；清零迁移 | 规格 §8 |

### 3.3 涉及模块与依赖

| 层 | 模块 | 依赖关系 |
|----|------|----------|
| 存储 | `history-v1`（14 天行为）、`progress-v1`（已练词条 + 毕业数） | 依赖既有 `LocalStore` 的读写与防御性校验约定 |
| 聚合 | `storage/ActivityAggregation.kt`（纯函数：周历七格、覆盖率、时长文案、14 天裁剪） | 无 Android 依赖 → **可单测** |
| 状态 | `AppState`：`history` / `progress` 状态 + `addStudySeconds` / `addCompletedTask` / `markVerbPracticed` / `recordMastered` + **启动回填** | 依赖 `daily-v1`（回填源）；被两个练习状态类调用 |
| 采集 | `StudyTimeTracker`（Composable，生命周期计时） | 依赖练习屏挂载；离屏写回 `AppState` |
| 导航 | `MainActivity`：`AppTab`（2）+ 二级页字符串常量 + `BackHandler` | 依赖两个练习状态类（状态提升在根级，进出不丢题） |
| 页面 | `HomeScreen`（重写）、`MineScreen`（新增） | 依赖聚合结果与 `AppState` |

关键依赖链：**出题/作答 → 采集（时长/任务/词条）→ 存储 → 聚合 → 主页周历条与我的页**。
其中「完成任务数」沿用第一次追加已实现的 `ROUND_SIZE = 5` 语义，两次追加在此处产生耦合。

## 4. 两次实现的异同与演进

### 4.1 相同点（同一套工作流）

1. 都先出**多版可交互原型**供选择，选定后才动生产代码
2. 都把口径写进**规格文档**再实现（文档先于代码）
3. 都按 **引擎/存储 → 状态 → UI** 分层推进，依赖单向
4. 都用**穷举式单测**锁死规则（5544 组合选项约束 / 7 格周历与 14 天裁剪）
5. 都做**模拟器实测**，且关键结论用**读设备存储文件**核对（不是只看界面）
6. 都在实测中抓到「看起来像坏了」的问题并修掉（见 §5）
7. 都遵守红线：引擎纯逻辑、颜色只在 `Theme.kt`、无 emoji 图标、存储键带版本号 + 防御性校验、测试基线不劣化
8. 都一次通过推送（仓库级 `http.sslBackend=schannel` + 本机代理）

### 4.2 不同点

| 维度 | 第一次追加 | 第二次追加 |
|------|-----------|-----------|
| 改动对象 | 单个界面 + 新引擎模块 | 导航结构 + 新增页面 + 数据模型 |
| 数据层 | **不新增存储键** | **新增 2 键 + 启动回填迁移** |
| 原型作用 | 选布局与图标方向（A/B/C 三版同一功能） | 选**信息组织方式**（三版差异在主视觉与信息密度） |
| 规格重点 | 像素级布局规格（尺寸/状态/动效） | 数据口径与采集方案（能否显示的前提） |
| 测试对象 | 引擎规则（选项唯一性、误形自证、位置随机） | 聚合纯函数（周历、裁剪、覆盖率、时长文案） |
| 迭代次数 | 落地后**3 次口径修正**（统计卡/环语义、Q7、Q8） | 落地后 0 次（一次到位） |
| 主要风险 | 交互语义理解偏差（抽屉「提交判定」的两种读法） | 数据口径缺口（三项指标算不出来） |

### 4.3 演进脉络

```
设计原型（3 版）→ 选定 → 规格 → 实现 → 实测
   ↓ 第一次追加
选择题界面落地（82af946，29 测试）
   ├── 口径对齐：统计卡 / 进度环 / 本轮统计（13862d6）
   ├── Q7 抽屉形态裁决（c5ed026，仅文档）
   └── Q8 选项来源收紧（0a894f0，31 测试）
   ↓ 第二次追加
两标签重设计 + 三项采集（7c4acb7，36 测试）
```

演进体现为三条线：

- **流程线**：从「单界面实现」到「IA 重构 + 数据扩展」，流程模板不变，但第二次提前增加了「数据口径盘点」这一步骤 —— 因为「我的」页有三项指标当时根本算不出来，这一步避免了大半工作量后才发现的返工。
- **测试线**：22 → 29 → 31 → 36。测试对象从纯引擎扩展到**可单测的聚合纯函数**（把逻辑从 Composable 里抽到 `ActivityAggregation`，是第二次追加的主动设计选择）。
- **收敛线**：第一次追加落地后出现 3 次口径修正，其中 Q7 是「改文档不改代码」——说明**把裁决写进规格**能让后续不再重复讨论；第二次追加因此一次到位。

## 5. 关键注意事项（实测踩过的坑）

### 5.1 交互与产品

1. **措辞要还原成交互语义**：「底部抽屉用于提交判定」存在两种读法（点选即判 / 两步确认）。选错会让整套交互与预期不符——凡遇歧义读法，先按最贴近字面的那版做原型，让用户点一下即可判断。
2. **不要用框架的双击手势做「双击提交」**：Compose 的 `detectTapGestures(onTap, onDoubleTap)` 会让单击延迟到双击超时（≈300ms）才回调，单击选中手感发粘。改为在点击回调里比较「同一选项 + 时间戳」（阈值取 `ViewConfiguration.getDoubleTapTimeout()` = 300ms）。
3. **选项来源必须收敛**：选择题的干扰项若混入无关词汇（如 来る 的题里出现「掃除します」），会变成"认词"而不是"辨形"。
4. **统计口径必须唯一**：同一组数字（答对/答错/正确率）在顶部统计卡与「本轮小结」里必须同源同公式，否则两处数字打架。

### 5.2 数据与存储

5. **新存储键上线要回填**：`history-v1` 首日为空会让主页周历显示 0，而打卡显示 3。做法：启动时若 history 今日答题数少于 `daily-v1`，取较大值补齐（幂等、只升不降）。
6. **不足 1 分钟要显示秒**：学习时长 `30 秒` 被 `秒 / 60` 取整显示成「0 分钟」，用户会以为没采集到。
7. **Kotlin `init` 块按声明顺序执行**：初始化逻辑若写在它读取的属性之前，会读到未初始化值。排查此类"代码看着对却没生效"的问题时，先确认声明顺序。
8. **防御性校验照旧**：两个新键都做了字段范围校验 + 去重 + 长度裁剪（14 天），坏数据回退空态并置 `lastLoadInvalid`。

### 5.3 工程与验证

9. **install 后必须 `am force-stop` 再启动**：`install -r` 不保证杀掉运行中的进程，旧代码仍在内存里，界面看起来"没生效"。
10. **`uiautomator dump` 可能返回上一次的旧文件**：关键判定用**截图**，或用 `rm -f /sdcard/ui.xml` 后重新 dump。
11. **adb 本地路径**：设了 `MSYS_NO_PATHCONV=1` 后 Windows 版 adb 无法解析 `/e/...`，`install` 会静默失败——本地路径用 `E:/...`，只有设备侧 `/sdcard/...` 需要禁转换。
12. **release 与 debug 签名不同**：`INSTALL_FAILED_UPDATE_INCOMPATIBLE`，必须先卸载。
13. **模拟器长跑会 system ANR**：软件渲染连跑两小时后 system 进程无响应，重启模拟器即可（不是应用问题）。
14. **验证要看到存储层**：`adb shell run-as <包名> cat files/<键>.json` 直接读设备上的数据文件——这是「采集是否真的落盘」的唯一硬证据，比看界面可靠。

## 6. 可复用要点（追加功能流程模板）

### 6.1 六步流程

| 步 | 动作 | 完成判据 |
|----|------|----------|
| 1 | **需求定调**：把用户措辞还原成可实现的交互/数据语义，识别歧义读法 | 歧义点列出来并按最贴近字面的一版做原型 |
| 2 | **原型供选**：同一功能的 2–3 版可交互原型（真实数据、可点、零脚本报错） | 用户选定（或混搭） |
| 3 | **口径/规格固化**：结构、区域、状态、令牌、数据口径、验收清单进规格文档 | 规格里能查到"为什么这么做" |
| 4 | **分层实现**：引擎/存储 → 状态 → UI，依赖单向；纯逻辑抽成可测函数 | 编译通过 |
| 5 | **穷举单测**：对规则做全量断言（不是抽样），测试基线只升不降 | 全绿且条数增加 |
| 6 | **实测 + 落盘核对 + 提交**：模拟器实测关键路径，读设备存储核对采集，提交并写清"改了什么/为什么/怎么验证的" | 截图 + 存储文件 + 提交记录 |

### 6.2 追加功能的检查清单

- [ ] 是否存在多种读法的需求措辞？→ 先做原型消除歧义
- [ ] 该功能依赖的数据**现在算得出来吗**？→ 先做数据口径盘点，算不出来的要先扩采集
- [ ] 是否新增存储键？→ 带 `-v1` 后缀 + 字段范围校验 + 缺失/坏数据回退
- [ ] 是否改动既有数据含义？→ 需要回填/迁移（幂等、只升不降）
- [ ] 新规则能否抽成纯函数？→ 抽出来配单测（Composable 里测不了）
- [ ] 是否有跨端一致性要求？→ 决定是否同步 Web（本项目口径：以 `docs/current-state.md` 为准）
- [ ] 颜色是否只出自 `Theme.kt`？图标是否只用 Material Icons？
- [ ] 测试基线是否只升不降？Web 82 与 Android 现有条数是否复跑过？
- [ ] 实测是否覆盖：正常路径 + 边界（空态/超长/未来日）+ 返回/切换后状态是否复位？
- [ ] 提交信息是否写清「改了什么 / 为什么 / 怎么验证的」？
