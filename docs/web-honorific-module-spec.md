## 2. 动词词库扩容（已实现）

### 2.1 改了什么

唯一数据位置：`web/verb-engine.js` 的 `VERBS` 常量（第 56 行起）。三段插入，保持原有的「五段 → 一段 → 不规则」分组顺序。

| 分组 | 原（79） | 第一批 | 授受动词 | 第二批（语体） | 现（173） |
| --- | --- | --- | --- | --- | --- |
| 五段（`kind: godan`） | 46 | +24 | — | +28 | **98** |
| 一段（`kind: ichidan`） | 24 | +13 | +2 | +12 | **51** |
| 不规则（`suru` / `kuru` / `iku`） | 9 | +8 | — | +7 | **24** |
| 合计 | 79 | +45 | +2 | +47 | **173** |

三批选词各有明确目的，第二批是第一次的补漏：

| 批次 | 类别 | 词例 | 挑选理由 |
| --- | --- | --- | --- |
| 一 | 补齐音便词尾 | 洗う・脱ぐ・磨く・貸す・勝つ・運ぶ・住む・登る | 原词库中「ぐ／つ／ぶ／ぬ」结尾各只有 1–2 个，音便题反复落在「書く」「泳ぐ」上；补完后除「ぬ」外每种词尾 ≥2 个 |
| 一 | 自他动词配对 | 開く／開ける・閉まる／閉める・見つかる／見つける | 自动词是他动词的天然对照，也让敬语「动作有没有意志」的口径有数据支撑 |
| 一 | サ変复合词 | 洗濯する・散歩する・説明する・確認する…共 8 个 | `kind: suru` 走「词干 + する」分支，加词零风险 |
| — | 授受动词 | あげる・くれる | 敬语形「差し上げる」「くださる」是最常用的两个特殊敬语，缺词条就出不了题 |
| 二 | **书面语／正式场合** | **行う**・設ける・含む・除く・示す・述べる・求める・与える・生じる・関わる・伴う・及ぶ・基づく・認める・定める | 第一批按「词尾音便 + 自他配对」挑词，没有按**语体**扫，导致书面语动词整类缺失（「会議を行う」「規則に基づく」这类句子一个词都没有）。第二批按语体补齐 |
| 二 | 复合动词 | 申し込む・引き受ける・取り消す・思い出す・出会う・間に合う・見直す・話し合う・落ち着く・思い付く・取り組む・見送る・呼びかける | 复合动词是 N3 的重点，且能覆盖「汉字同形、读音不同」的坑（行う vs 行く） |
| 二 | 情感与日常动作 | 招く・断る・謝る・頼む・許す・叱る・驚く・喜ぶ・怒る・届ける・預ける・迎える | 第一批几乎没有情绪类动词，例句与「〜たい／〜てしまう」类练习用不上 |
| 二 | 业务サ変复合 | 案内する・相談する・報告する・提出する・検討する・対応する・利用する | 敬语模块的场景例句需要这批词（「ご報告します」「ご対応いただく」） |

**刻意不加「ある」。** 引擎的统一规则会把它算成「あらない」，而正确否定是「ない」；这需要新增一种 `kind` 与专属分支，属于引擎改造，不与本次纯数据扩充混在一起。同理，「くださる」「おっしゃる」「いらっしゃる」这类敬语专用动词的ます形是「くださいます」（不是「くださります」），留给敬语模块的 `kind: honorificSpecial` 处理。

## 3. 敬语模块设计构思

### 3.1 教学口径：先判主体，再选敬语

敬语的学习难点不是变形，而是**选哪一类**。模块把判断压成三问，顺序固定：

| 顺序 | 问题 | 答案 → 敬语种类 | 例 |
| --- | --- | --- | --- |
| 1 | 这个动作是**对方或上位第三方**做的吗？ | 是 → 尊敬語 | 先生が**お書きになる** |
| 2 | 这个动作是**自己或己方**做的吗？ | 是 → 謙譲語 | 私が**お書きします** |
| 3 | 只是把话说得体面，不涉及抬高谁？ | 是 → 丁寧語 | **書きます** |

配套两条硬规则，模块必须显式教：

- **内外关系**：客户在场时，自己公司的上司也算「己方」，对他的动作要用謙譲語（「部長が申しておりました」），不能用尊敬語。这是最容易错的一条，做成独立判断题。
- **无意志动词不接敬语**：「雨が降っていらっしゃる」「花がお咲きになる」都不自然。敬语只对可控动作成立。词库中 8 个无意志/自然现象动词（降る・咲く・分かる・見つかる・始まる・終わる・開く・閉まる）标记为 `limited`，只出丁寧語，并在结果里说明原因，而不是给出错误答案。「疲れる」（お疲れになる）与「生まれる」（お生まれになる）实际成立，不列入。

### 3.2 适用场景

场景是筛选维度，也是例句卡的标签。每个场景给出「谁对谁」，因为敬语的正确性取决于人际关系而不是句子本身。

| 场景 ID | 场景 | 谁对谁 | 该用 |
| --- | --- | --- | --- |
| `work` | 职场·上司 | 部下 → 上司 | 尊敬語为主，自述用謙譲語 |
| `client` | 职场·客户 | 社内 → 社外 | 对外部用尊敬語，对本公司上司也用謙譲語（内外规则） |
| `shop` | 店·服务 | 店员 ↔ 顾客 | 店员对顾客全用尊敬語；顾客对店员用丁寧語即可 |
| `phone` | 电话·邮件 | 对上级/客户 | 开头「お世話になっております」+ 謙譲語自述 |
| `visit` | 拜访·接待 | 访客 ↔ 主人 | 访客自述謙譲語（伺う・参る），主人对访客尊敬語 |
| `daily` | 日常礼貌 | 邻居·陌生人 | 丁寧語为主，少量尊敬語 |

每个场景配 4 条例句卡（6 × 4 = 24 条），只用手写固定例句，不调用任何模型——模块保持离线可用，不引入成本。

### 3.3 触发方式

分三层，互不依赖：

| 层 | 触发 | 说明 |
| --- | --- | --- |
| 入口 | 侧栏「学习」组新增「敬语」→ 打开动词模块的敬语子页 | 不新增顶层 view id（复用 `verb`），侧栏只换 subview 目标；主页模块卡同样指向该子页 |
| 学习链路 | 动词练习的反馈面板末尾加「看它的敬语说法 →」 | 刚答完普通形，紧接着看三层对照，是最自然的衔接点 |
| 内容判定 | 敬语子页内的「敬语诊断器」：选动词 + 选主体（我/对方）+ 选听话人（上司/同事/客户/陌生人） | 输出该用哪一类、推荐形态、一句理由；这是把 3.1 的三问变成可操作工具 |

不做「自动判断用户输入句子的敬语是否正确」——那需要形态素分析，超出离线静态站的能力边界。只做**词表级**的二重敬语检测（见 3.4）。

### 3.4 展示形式

四块，从查到练：

1. **三层对照表**（速查主体）
   列为：普通形 / 尊敬語 / 謙譲語 / 丁寧語。每格标「规则形 / 特殊形」，特殊形高亮并给出规则形的替代说法（如「食べる」：召し上がる（特殊，常用）／お食べになる（规则，较少用））。
2. **场景例句卡**
   日文 + 假名 + 中文 + 「谁对谁」标注 + 敬语种类徽标。卡片底部可直接「练这句里的动词」，跳到对应题目。
3. **练习反馈**（沿用现有 `feedback-panel` 结构）
   正确形态 + 读音 + 为什么用这一类 + 常见错误。例如答「ご説明します」而正确答案是「ご説明いたします」时，提示「する 的謙譲語更礼貌形式是 いたす」。
4. **二重敬语警示**
   在诊断器输入框里对输入文本做词表匹配，命中即提示并给正确说法：

   | 错误 | 正确 | 原因 |
   | --- | --- | --- |
   | おっしゃられる | おっしゃる | おっしゃる 本身已是尊敬語，不接 られる |
   | ご覧になられる | ご覧になる | 同上 |
   | お召し上がりになられる | 召し上がる | 双重叠加 |
   | 拝見させていただきます | 拝見します | 拝見 已含謙譲，不再叠 させていただく |
   | お伺いいたします | 伺います / お伺いします | 伺う 已含謙譲，择一 |

### 3.6 数据与引擎设计

新增 `web/honorific-engine.js`，纯逻辑 UMD，禁 DOM / 存储 / 网络，复用 `JapaneseVerbEngine.conjugate` 取ます词干。

```js
// 三层定义
HONORIFIC_LEVELS = [
  { id: "sonkeigo", label: "尊敬語", question: "谁做的？对方 → 抬高对方动作" },
  { id: "kenjougo", label: "謙譲語", question: "谁做的？自己/己方 → 压低自己动作" },
  { id: "teineigo", label: "丁寧語", question: "只是礼貌体 → ます形" }
]

// 规则派生（按 kind 分派，与 verb-engine 的 kind 体系对齐）
buildRuleForm(verb, levelId):
  sonkeigo: godan/ichidan → "お" + masuStem + "になる"
            suru          → "ご" + 漢語词干 + "になる"
  kenjougo: godan/ichidan → "お" + masuStem + "する"   // 更礼貌档：+ "いたす"
            suru          → "ご" + 漢語词干 + "する"
  teineigo: 直接取 masu 形

// 特殊敬语动词表（手工，15 条，不走规则）
SPECIAL_HONORIFIC = {
  iku:      { sonkeigo: ["いらっしゃる", "おいでになる"], kenjougo: ["参る", "伺う"] },
  kuru:     { sonkeigo: ["いらっしゃる", "お見えになる"], kenjougo: ["参る"] },
  iru:      { sonkeigo: ["いらっしゃる", "おいでになる"], kenjougo: ["おる"] },
  taberu:   { sonkeigo: ["召し上がる"], kenjougo: ["いただく"] },
  nomu:     { sonkeigo: ["召し上がる"], kenjougo: ["いただく"] },
  miru:     { sonkeigo: ["ご覧になる"], kenjougo: ["拝見する"] },
  iu:       { sonkeigo: ["おっしゃる"], kenjougo: ["申す", "申し上げる"] },
  suru:     { sonkeigo: ["なさる"], kenjougo: ["いたす"] },
  shiru:    { sonkeigo: ["ご存じです"], kenjougo: ["存じる", "存じております"] },
  morau:    { sonkeigo: [], kenjougo: ["いただく", "頂戴する"] },
  ageru:    { sonkeigo: [], kenjougo: ["差し上げる"] },
  kureru:   { sonkeigo: ["くださる"], kenjougo: [] },
  kiku:     { sonkeigo: [], kenjougo: ["伺う", "拝聴する"] },
  au:       { sonkeigo: [], kenjougo: ["お目にかかる"] },
  shinu:    { sonkeigo: ["お亡くなりになる"], kenjougo: [] }
}

// 无意志动词白名单：只出丁寧語，结果里说明原因
LIMITED_VERBS = ["furu", "saku", "wakaru", "mitsukaru", "hajimaru", "owaru", "aku", "shimaru"]

// 判定器
judgeLevel({ subject, listener, scene }) -> { levelId, reason, alternatives }

// 二重敬语检测
checkDoubleHonorific(text) -> { ok, issues: [{ phrase, suggestion, reason }] }
```

关键正确性约束（写进引擎注释与测试）：

1. 特殊形优先于规则形。`getHonorific(verb, levelId)` 返回 `{ primary, alternatives, isSpecial }`，`primary` 取特殊形，规则形进 `alternatives`。
2. `limited` 动词的 `sonkeigo` / `kenjougo` 返回 `{ unavailable: true, reason: "..." }`，不返回编造形态。
3. サ変复合词的漢語词干取 `dictionary` 去掉「する」（「説明する」→「説明」），与 `verb-engine` 的 `kind: "suru"` 分支口径一致。
4. 判题复用 `normalizeAnswer`，接受「お書きになる」「おかきになる」「okakininaru」；`alternatives` 中每条都算对。

用户可感知的变化：

- 「書く」这类词的练习不再止于「書ける／書かれる／書かせる」，而是延伸到「お書きになる／お書きする」，形成完整的礼貌层级认知。
- 敬语不再是背一张特殊动词表，而是先判主体、再选类别、最后才是形态。
- 答错时能拿到「为什么该用这一类」的理由，而不只是「正确形态是 X」。

### 5.2 与设计的三处偏差（如实记录）

1. **配置面板未做。** §3.5 的 8 项设置全部按默认值运行，`japanese-honorific-config-v1` 未创建。原因是首版先验证教学口径与练习闭环，配置属于体验优化；登记为 IK-24。
2. **错题不进全局错题本。** 设计写的是「默认并入」，实现改为当前会话重练队列（答错后下一题重现该题），刷新即丢。理由是错题本需要第三分组与 `questionFromMistake` 分支，改动面比预期大；题 key 已按 `hon::` 前缀备好，接入时只需补这两处。登记为 IK-25。
3. **判题只认ます形。** 设计里「目标形式」是可配置项（辞书形／ます形／混合），实现固定为ます形——敬语离开礼貌体几乎不成立，先砍掉这一维避免配置爆炸。

### 5.3 计划外的工作

- 词库补 2 个授受动词（あげる・くれる）：特殊敬语表要收「差し上げる」「くださる」，缺词条就无法出题。
- 词库第二批 +47（书面语、复合动词、情感类、业务サ変），最终 **173 词**；起因是关子问「为啥没有 おこなう 这种」——第一批按词尾音便挑词，漏了整个书面语语体。
- 侧栏高亮原本会让「动词活用」与「敬语」同时是当前页；修在 `showView` 的 tabs 循环里按子视图区分。
- 页面大标题（`renderIntro`）原本在子视图切换时不刷新；`setVerbSubview` 末尾补一次重渲染，并为敬语写了独立文案组。
